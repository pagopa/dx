Expected outcome of the initiative

The outcome API accepts PSP callbacks and must turn each logical payment into at most one user-visible notification, even when the PSP retries the same delivery. Today a retried webhook can enqueue two notifications because the worker has no way to recognize that it already saw the event.

Solution design

The gateway computes an idempotency key from the PSP delivery id and stores it in a Redis-backed outcome store before the worker runs. A duplicate key returns the stored response and is never re-enqueued.

Record of decisions

  • ADR-014 proposes keying on the PSP delivery id, not on the payment id.

  • ADR-015 proposes keeping the dedup window at 24 hours.

Decisions in the collapsible section above are proposals pending review; they are not yet approved.
