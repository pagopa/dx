# Tooling Lifecycle & Support

This page is the **single source of truth** for the lifecycle status of all
tools maintained or supported by the DX team. It defines what "supported" means,
how lifecycle decisions are made, and tracks the current status of each tool
version.

## What Does "DX Support" Mean?

When DX declares a tool version as **supported**, we commit to:

- **Pipelines**: CI/CD reusable workflows are tested and guaranteed to work with
  that version.
- **Terraform modules**: DX modules on the Terraform Registry are compatible and
  tested.
- **DX CLI**: The `dx` CLI operates correctly with that version.
- **Devcontainers**: DX devcontainer templates include and configure that
  version.

When a version reaches **End of Life (EOL)**, DX no longer guarantees
compatibility and may remove support at any time.

## How Lifecycle Transitions Are Communicated

Lifecycle transitions are communicated through:

- DX periodic bulletins (DX Newsletter)
- Tool-specific channels listed in each tool section below

## Status Definitions

| Status          | Meaning                                                      |
| --------------- | ------------------------------------------------------------ |
| **Active**      | Fully supported. Recommended for production use.             |
| **Maintenance** | Supported but nearing end of life. Start planning migration. |
| **Deprecated**  | Support will end soon. Migrate as soon as possible.          |
| **End of Life** | No longer supported. May break without notice.               |

## Preparing for AzureRM v5-only module releases

DX tooling's AzureRM v4 support window ends on **31 December 2026**. Upcoming
major releases of the twenty DX modules that already support both v4 and v5
are planned to require `hashicorp/azurerm ~> 5.0`. This is a
future release plan, not an announcement that these majors are already
published. Older dual-compatible module versions remain usable during the
published v4 support window.

The planned change does **not** migrate the v4-only `azure_api_management`,
`azure_app_service`, `azure_function_app`, `azure_core_infra`, or
`azure_storage_account` modules. Do not upgrade a root configuration to v5
until all its modules and transitive dependencies support v5. Keep using a
compatible module version while those dependencies are being migrated.

When adopting a v5-only module major, retain Terraform **>= 1.16.0** (or any
higher minimum already required by your configuration), update the root
provider requirement, and select compatible versions of every module:

```hcl
terraform {
  required_version = ">= 1.16.0"

  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 5.0"
    }
  }
}
```

Run `terraform init -upgrade` to refresh `.terraform.lock.hcl`, commit the
updated lockfile, and review `terraform plan` before applying. Follow the
[AzureRM v5 upgrade guide](https://registry.terraform.io/providers/hashicorp/azurerm/latest/docs/guides/5.0-upgrade-guide)
for provider-specific changes in your own resources. Removing v4 support
does not itself rename DX module resources or require state address changes.
