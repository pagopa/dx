# Code Review with Nx

The reusable
[`validate-v2.yaml`](https://github.com/pagopa/dx/blob/main/.github/workflows/validate-v2.yaml)
workflow runs affected Nx checks and Terraform plans. Repositories generated by
`dx init` already call it. Fork pull requests remain blocked by its existing
fork gate.

## Optional Amazon ECR Public authentication

Without AWS configuration, pulls from `public.ecr.aws` remain anonymous.
To use authenticated download quotas, make this **optional GitHub Actions
secret** available to the calling repository:

| Secret                | Value                                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------- |
| `ECR_PUBLIC_ROLE_ARN` | ARN of an existing AWS IAM role that GitHub Actions can assume through OIDC for ECR Public pulls. |

Share an organization secret with the repository, or configure a repository
secret. Do not configure it only as an environment secret: the gate and the
validation job without an environment must also see it. Environment jobs must
resolve the same role; avoid overriding this secret in GitHub environments.

This follows the existing AWS OIDC authentication pattern; no static
`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, or `AWS_SESSION_TOKEN` secrets are
required. The existing Terraform `ROLE_ARN` and `AWS_REGION` secrets are
independent and are not used to opt in to registry authentication.

### Caller configuration

`pagopa/dx` already uses `secrets: inherit`. Other callers can use inheritance
where GitHub permits it (within the same organization or enterprise), or add
the optional secret to their existing explicit secret mapping:

```yaml
jobs:
  validate:
    permissions:
      actions: read
      contents: read
      id-token: write
      packages: read
      pull-requests: write
    uses: pagopa/dx/.github/workflows/validate-v2.yaml@main
    secrets:
      ECR_PUBLIC_ROLE_ARN: ${{ secrets.ECR_PUBLIC_ROLE_ARN }}
      # Keep any existing Azure, Terraform and GitHub App secret mappings.
```

`id-token: write` must be granted by every caller in a reusable-workflow
chain, and the secret must be forwarded through every hop. New `dx init`
scaffolds include the optional mapping. Existing callers need no changes
unless they want to enable authenticated pulls.

### AWS and runner prerequisites

The role must already have permission for `ecr-public:GetAuthorizationToken`
and `sts:GetServiceBearerToken` on `*`. Its trust policy must allow
`sts:AssumeRoleWithWebIdentity` from the GitHub OIDC provider, with audience
`sts.amazonaws.com`, restricted to the intended caller repository and execution
contexts. For standard GitHub OIDC subjects, these include:

- `repo:OWNER/REPO:pull_request` for the job without an environment.
- `repo:OWNER/REPO:environment:ENVIRONMENT` for each environment job, such as
  `infra-prod-ci` or `bootstrapper-prod-ci`.
- The allowed branch subjects for manual runs, such as
  `repo:OWNER/REPO:ref:refs/heads/main`.

Adapt these subjects if the organization uses custom OIDC claims. Do not
broaden trust to other repositories or use `pull_request_target` to expose
credentials to fork code. This workflow does not change the fork gate or
GitHub's secret restrictions, including those for Dependabot pull requests.

Runners must already provide a working Docker client and access to GitHub
OIDC, AWS STS and the ECR Public endpoints. No runner or Azure infrastructure
changes are required or provisioned by this workflow.

### Execution and limits

When the secret is available, both validation jobs assume the dedicated role
and log the local Docker client into `public.ecr.aws` **before** running the
affected checks, including Docker builds and Trivy OCI downloads. ECR Public
token requests always use `us-east-1`, regardless of the Terraform region.
The temporary AWS credentials are scoped to the login step, so existing
Terraform credentials and regions are preserved. The ECR login action masks
the registry password and logs Docker out during post-job cleanup.

When the secret is missing or withheld, AWS setup and registry login are
skipped and existing anonymous behavior is retained. Once configured, role
assumption or registry login errors fail the job; they do not silently fall
back to anonymous access. Authentication uses AWS's authenticated quotas,
not unlimited downloads, and cannot authenticate images pulled by GitHub
before job steps start (for example a job container or service).
