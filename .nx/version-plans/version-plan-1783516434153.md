azure_api_management: major
---

Simplify the Azure API Management module contract for the next major release. The module now owns APIM subnet creation, public IP creation when required by the selected use case, private DNS zone lookup in the current subscription, monitoring defaults, management locks, publisher notifications, Application Insights connection string lookup, and simplified hostname certificate inputs.

### Migration from 4.x to 5.x

- Replace the `virtual_network` name/resource-group object with the full virtual network resource ID. Remove `subnet_id` and `subnet_pep_id`: the module creates the APIM /24 subnet, delegates it to `Microsoft.Web/serverFarms` for `cost_optimized` Standard v2 outbound integration, and derives the private endpoint subnet ID using the standard `pep` subnet name. The private endpoint uses its separate, nondelegated subnet.
- Remove `virtual_network_type_internal`, `enable_public_network_access`, and `public_ip_address_id`. Networking is selected by `use_case`; `high_load` creates a Standard static public IP, while `cost_optimized` uses a private endpoint. Review the network changes before applying.
- Remove `private_dns_zone_ids`. The module computes fixed Azure API Management zone names and the private endpoint zone ID from the VNet subscription and `private_dns_zone_resource_group_name` (defaulting to the VNet resource group).
- Replace `monitoring` with `log_analytics_workspace_id`, required for `cost_optimized` and `high_load`. Existing metric-alert defaults and the `metric_alerts` / `metric_alert_thresholds` overrides are preserved.
- Remove `notification_sender_email` and `lock_enable`. Notifications use `publisher_email`; management locks are enabled for production use cases and disabled for `development`.
- Remove `management_logger_application_insight_enabled`, `application_insights.enabled`, and `application_insights.connection_string`. Set `application_insights` to `null` to disable the integration, or provide an object with a required `id` to enable it; the module resolves its connection string internally. The nullable object lets callers pass an ID that is unknown until apply without making resource counts unknown during planning.
- Remove `key_vault_id` and `certificate_names` only after transferring the existing APIM client certificates to caller-managed resources, as described below. Client certificates are separate from hostname TLS certificates.
- Rename each custom hostname's `key_vault_id` to `key_vault_certificate_id`; versioned certificate IDs are normalized internally. Replace the `hostname_configuration.proxy` list with `{ use_resource_name_as_default = true }` if needed; the proxy hostname is always the APIM resource-name hostname.
- Update the module version constraint to `~> 5.0`. This contract layer retains AzureRM v4; the stacked provider migration supplies AzureRM v5 before the single major release.

Existing deployments need special care: the new module-managed subnet and public IP are not automatically adopted from caller-managed resources. Review a Terraform plan and migrate ownership explicitly where appropriate to avoid unintended subnet conflicts or APIM replacement. No state migration is performed automatically.

#### Preserve existing APIM client certificates

The 4.x module created `azurerm_api_management_certificate.this` instances from
`key_vault_id` and `certificate_names`. Hostname TLS bindings do not replace
these resources. Transfer every existing certificate before applying the
upgrade, or Terraform will plan to delete it.

1. Pause automated Terraform runs and securely back up the state. In each
   affected workspace, use `terraform state list` and `terraform state show`
   to record each certificate's exact address, ID, name, APIM name, resource
   group, and `key_vault_secret_id`. Match count indices to the actual state,
   not to a potentially reordered `certificate_names` list.
2. Add caller-managed resources using the same AzureRM provider configuration,
   APIM name, resource group, and certificate names. Map each name to its exact
   existing Key Vault **secret** ID from state, including any trailing slash;
   do not substitute a certificate ID or secret value. For example, replace the
   placeholders below with the existing values and adjust the module references
   for the caller's configuration:

   ```hcl
   locals {
     existing_apim_client_certificates = {
       "existing-name" = "https://example.vault.azure.net/secrets/example/"
     }
   }

   resource "azurerm_api_management_certificate" "client" {
     for_each = local.existing_apim_client_certificates

     name                = each.key
     api_management_name = module.apim.name
     resource_group_name = module.apim.resource_group_name
     key_vault_secret_id = each.value
   }
   ```

3. Prepare the module upgrade and initialize the configuration without applying.
   Move each certificate's state binding to its new address before any apply:

   ```sh
   terraform state mv \
     'module.apim.azurerm_api_management_certificate.this[0]' \
     'azurerm_api_management_certificate.client["existing-name"]'
   ```

   Substitute the actual addresses, including module instance keys, and repeat
   for every certificate in every affected workspace. After each move, use
   `terraform state show` on the destination and compare its ID with the
   recorded original. The move preserves the Azure certificate and its ID
   without deleting or recreating it. Preserve the APIM identity and its Key
   Vault access as well.
4. Review a fresh full Terraform plan. Do not apply if it creates, deletes, or
   replaces an existing certificate or the APIM instance, or makes unintended
   certificate updates. Resolve any separate subnet and public IP migration
   issues before applying.
