Use domain-specific Terraform state containers and layer-based state keys for
new environments. Prepare managed containers through ARM, grant the current user
container-level Blob Data Contributor, and verify write and lease access before
initialization. Preserve resolvable existing backend files, coordinates and keys;
check existing core state read access without direct CLI role assignments.

## Migration guide

New environments use `<domain>-tf-state` and `<prefix>-tf-state` rather than the
previous shared-container convention. Domains must contain 3-54 lowercase
letters, numbers and single hyphens, with alphanumeric endpoints; update
previously accepted non-compliant workspace configuration explicitly before
upgrading.

Existing remote state is not moved automatically: retain its configured
coordinates and keys. If a backend migration is intended, suspend state writes,
back up the state, prepare destination and upstream access, migrate explicitly
with `terraform init -migrate-state`, and verify state and dependent consumers
before removing old access.

Backend discovery supports existing Terraform roots marked by `main.tf` under
direct layer/environment roots and the tenant layout
`<layer>/<lifecycle>/<domain>`, including nested project directories. For roots
outside the CLI-generated `bootstrapper` and `core` layers, missing backend
files are created with a state key derived from the layer and relative root
path. Existing backend configuration is preserved byte-for-byte. Dynamic or
unresolved coordinates, multiple backends in one root, and duplicate state
locations stop generation before backend files are written. Roots with local
state or `.terraform` backend metadata require an explicit state migration
before a remote backend can be added, even without `main.tf` in bootstrapper/core.
Checks based on existing files run before cloud or GitHub writes; collisions
involving derived backend coordinates are checked once resolved, before writing
backend files.
Reruns after cloud initialization generate a missing core root while preserving
existing core roots and avoiding repeated cloud initialization. Generated common
resource imports omit the workspace domain, matching the core module naming.

Generated bootstrapper roots opt into the bootstrap module's container-scoped
state access, using the effective backend container name so existing coordinates
are preserved; new backends use the domain-derived name. When the root consumes
core state, the module configuration grants Reader to `infra_ci` and `infra_cd`
at the resolved core container, unless it is already the own-state container.
Cross-account upstreams use the exact ARM container ID. The operator or
bootstrapper identity running the first plan still requires Reader prepared
manually. The template provisionally pins bootstrap `~> 7.2`, expected from
#2509 and coordinated with #2508. It is not published or verified yet; confirm
the Registry release and update the pin if needed before merging or releasing
the CLI. Registry-based Terraform validation and planning remain gated until
then.
Repository-state migration remains a separate change and must be reconciled
before publishing the complete flow.
