La tesi

Il collo di bottiglia non è più il codice.
È il contesto.

Gli agenti amplificano ciò che trovano: un contratto lo ereditano, una convenzione non scritta la reinventano.

01
Ereditarietà

Le convenzioni si ereditano, non si leggono

Un'astrazione è conoscenza compressa: massima precisione, minimo contesto.

02
Governabilità

Centralizzato = aggiornabile

Ciò che è sparso per repository è conoscenza che scade in silenzio.

Conseguenza: ogni standard reso esplicito si moltiplica per ogni agente e ogni team che lo usa.

Repository interocontesto massimo
Documentazione + modulicontesto mirato
Skill + MCP + contratticontesto minimo
Stessa accuratezza, una frazione del contesto. token ↓ · tempo ↓ · variabilità ↓
Il valore delle astrazioni, in epoca agentica

Cinque ragioni economiche

01 · Manutenzione

Update centralizzati

Un fix nel modulo arriva a tutti i repository. Renovate propaga le versioni. Il costo è O(1) per piattaforma, non O(n) per repo.

02 · Compliance

Determinismo e governance

Naming, CIDR, tag, IAM e policy derivano da contratti. Stesso input → stesso output, per umani e agenti. La governance è codice.

03 · Organizzazione

Bus factor ↓

La conoscenza sta in moduli, skill, documentazione e MCP, non nelle teste. Onboarding = clonare e leggere gli artefatti.

04 · Agenti

Contesto ↓ → token e tempo ↓

L'agente carica contratti mirati invece di esplorare il repository. Meno contesto significa meno token, meno latenza, meno variabilità.

Stima illustrativa su un task tipo "storage con private endpoint": esplorazione libera vs artefatti DX.

Democratizzazione della produzione

LAYER 00

Toolchain del monorepo

Il contratto che dx-cli init scaffolda: tutto il resto lo presuppone.

✓ Un solo task graph. Nx orchestra build, test, lint e typecheck di TypeScript, Go, Python e Terraform con cache e affected.
✓ Un solo toolchain. mise + lockfile fissano Node, pnpm, Terraform, TFLint, Trivy, terraform-docs, pre-commit e gh: macchina, devcontainer e CI eseguono le stesse versioni.
✓ Un solo contratto di struttura. apps/, packages/, infra/{repository,bootstrapper,core,resources}, docs/: gli agenti sanno sempre dove guardare.
✓ Qualità alla fonte. Pre-commit con hook DX e pre-commit-terraform: format, validate, tflint, trivy e lock di provider e moduli.
✓ Agenti configurati dal repository. .github/copilot/settings.json abilita marketplace e plugin DX: zero setup per sviluppatore, nessun drift di configurazione.

Perché è il layer zero: un agente che trova sempre la stessa struttura non deve indovinare dove intervenire. È il prerequisito di ogni automazione successiva.

Ruoli e permessi

Gruppi per responsabilità

admin (Contributor, Key Vault Secrets Officer), developers (Reader, Monitoring Contributor), externals (Reader). Il gruppo vpn apre le risorse private.

Zero secret statici

OIDC federated identity

I workflow si autenticano su Azure e AWS con federated identity. Niente password né service principal da ruotare: la fiducia è un contratto tra GitHub e il cloud.

Esecuzione

Runner self-hosted

Container Apps Jobs su Azure, CodeBuild su AWS. Rete privata, cache e toolchain identica alla CI. Un runner per prodotto, gestito da una GitHub App dedicata.

Risultato: un nuovo prodotto ha repository, ambienti, permessi, runner e pipeline in una sessione interattiva — e ogni passo è riproducibile.

LAYER 02

Core & Hub

Infrastruttura di piattaforma per ambiente: si applica una volta, la usano tutti i team.

Core · infra/core/<env>
⌁ Networking — VNet, subnet e private endpoint con CIDR derivati.
⌁ DNS privato — zone gestite centralmente e consumate dai servizi.
⌁ VPN cross-cloud — connettività AWS ↔ Azure con modulo dedicato.
⌁ Log Analytics e App Insights — destinazione di default di trace e metriche.
⌁ Policy — guardrail di subscription e valori esportati agli altri layer.
Hub · infra/resources/<env>
◇ API gateway — API Management: punto di ingresso unico e policy di accesso.
◇ Key Vault — segreti referenziati dalle app, mai nei valori di configurazione.
◇ Messaggistica condivisa — namespace per le integrazioni asincrone tra servizi.
◇ Consumo per team — ruoli e valori pronti; le risorse applicative vivono nel repo del prodotto.

I servizi dati (database, cache, storage) sono risorse del team, composte con i moduli DX — non infrastruttura condivisa.

Confine chiaro: core e hub sono a carico della piattaforma; i team compongono le proprie risorse e ricevono ruoli e valori già pronti.

Perché è una piattaforma e non una collezione di tool

Un deploy attraversa tutti i layer

Esempio: la release di citizen-api su Container App. Ogni layer consuma i contratti di quello sotto — nessuno è decorativo.

L01 · BOOTSTRAP IAM del deploy Il job entra nel GitHub Environment dev-cd via OIDC federated identity: ruoli e permessi creati dal bootstrapper decidono chi può fare cosa. Nessun secret da copiare o ruotare.
L00 · TOOLCHAIN Build riproducibile pnpm nx build citizen-api usa la toolchain fissata da mise e lockfile, con cache e affected: la stessa build della macchina locale, eseguita in CI.
L03 · MODULI Configurazione Il modulo azure_container_app espone le opzioni del servizio: immagine, variabili, segreti da Key Vault, scale.
L04 · PIPELINES Orchestrazione Il workflow riusabile release-azure-containerapp-v1 applica quelle opzioni: build, push dell'immagine, deploy della revision. Zero YAML duplicato nei repository dei team.
L02 · CORE & HUB Destinazione Key Vault, API gateway e rete privata esistono già nell'ambiente: l'app si aggancia ai servizi condivisi senza cablaggi manuali.
L06 · OSSERVABILITÀ Feedback La nuova revision traccia su Application Insights e le dashboard OpEx si rigenerano dal contratto OpenAPI: il ciclo si chiude sul comportamento reale.

Rimuovi un layer e il deploy torna a essere un lavoro da esperti: IAM gestito a mano, build non riproducibile, configurazioni divergenti tra ambienti, nessun feedback in produzione.

Principio di progettazione

Standard che le macchine già conoscono,
niente costruzioni magiche.

L'astrazione vive nei moduli e nei workflow, non in un runtime proprietario. Nessun DSL custom: solo tecnologie documentate, versionate e indipendenti dalla piattaforma.

NON NE ABBIAMO BISOGNO
✕ DSL proprietario da imparare: gli agenti non l'hanno mai visto nei dati di training e lo allucinano.
✕ Runtime di scaffolding interno: un altro sistema da mantenere, versionare e spiegare.
✕ Portale come unica fonte di verità: non è diff-abile, non è versionato, non è testabile in CI.
✕ Lock-in non necessario: uscire dalla piattaforma diventa più costoso che restarne dentro.
LA NOSTRA SCELTA
✓ Terraform per l'infrastruttura, GitHub Actions per le pipeline, Nx per il monorepo.
✓ OpenTelemetry per l'osservabilità, OpenAPI per i contratti, MCP e Agent Skills per gli agenti.
✓ mise per gli ambienti, pnpm per i workspace, pre-commit per la qualità locale.
✓ Conseguenza: gli agenti sono già competenti, le persone non ripartono da zero, l'uscita resta possibile.

Discovery → PRD

Trasforma il materiale grezzo in un PRD a esiti

Attori, JTBD, metriche, guardrail, vincoli e domande aperte. Il passaggio draft → review avviene solo su conferma esplicita: l'agente non promuove sé stesso.

ID stabili: metadata.* · JTBD-XX · output pronto per Confluence
<!-- PRD-02-NEED -->
| JTBD-01 | "Come PM voglio … per …" |
| metadata.status | draft · promozione solo su conferma |
PRD / RFC → DR·SRS

Il progetto operativo, non l'idea

Confini, componenti, contratti, NFR, rollout, monitoraggio. Un RFC accepted non guida l'implementazione finché la decisione non è propagata nel DR/SRS.

Fonte di verità unica: il DR/SRS, con catalogo UC-XX
<!-- DR-BOUNDARIES -->
| UC-01 | Checkout | P1 |
RFC-12 accepted → decisione propagata nel DR/SRS
DR/SRS → Use Case

Comportamento implementabile e testabile

Flussi principali, alternativi ed eccezioni, postcondizioni e acceptance check binari. Gli attori sono copiati esattamente dal PRD; i conflitti restano visibili come domande aperte.

AC-UC-XX-YY binari · ogni UC aggiorna il catalogo del parent

  allora l'ordine è creato.

Epic coerenti da pochi sprint, Story orientate al valore, Task abilitanti separati. Definition of Ready verificata prima di creare qualunque item.

Pubblicare senza perdere struttura

Gerarchie, tabelle, link, ID e stato del documento restano intatti. Le operazioni irreversibili richiedono conferma esplicita; la pubblicazione non cambia il lifecycle.
